# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This is a no-build, no-framework, single-canvas browser game
(`index.html` / `style.css` / `game.js`). There is no React/Next/Vite/component
framework and no `components.json` — the `<shadcn_gate>` from the researcher
playbook is **not applicable** and was not run. This contract governs (1) the
existing DOM chrome (HUD bar, buttons, overlays) exactly as far as this phase
touches it, and (2) a new "Canvas Render Contract" section specific to the
chase-cam renderer, since the template's generic Spacing/Typography/Color
sections alone don't capture what the executor needs to build RENDER-01..04.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, HUD chip inline padding |
| sm | 8px | Compact element spacing, HUD bar internal gaps |
| md | 16px | Default element spacing, touch control gaps |
| lg | 24px | Section padding |
| xl | 32px | Layout gaps |
| 2xl | 48px | Major section breaks |
| 3xl | 64px | Page-level spacing |

Exceptions:
- Existing `.game-hud` padding is `7px 14px` (legacy, off-scale, pre-existing — not touched by this phase; grandfathered, do not "fix" incidentally while doing renderer work).
- Existing `.touch-btn` height is `68px` (legacy touch target, already exceeds the 44px minimum — grandfathered, unchanged).
- Any **new** HUD/canvas-overlay element this phase adds (e.g. a restyled lap/position chip per D-13) must use the 8-point scale above, not match the legacy off-scale values.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 12px | 700 | 1.2 |
| Body | 16px | 700 | 1.3 |
| Heading | 40px | 900 | 1.05 |
| Display | 96px | 900 | 0.95 |

Usage mapping:
- **Label (12/700/1.2)** — secondary HUD tags: role/gap indicator (`hud-role`, e.g. `-1.2s` / `LÍDER` / `HOST`), small captions.
- **Body (16/700/1.3)** — primary HUD readouts: lap counter (`hud-lap`), position badge (`hud-pos`), race timer (`hud-timer`). Slightly larger than today's `0.7rem`/`0.95rem` — legibility matters more once the player's eyes are tracking a moving 3D road, not a static top-down map.
- **Heading (40/900/1.05)** — canvas-drawn overlay subtitles: `¡GO!`/`¡Buen intento!`-class secondary lines, and the new test-loop name label in the countdown overlay (see Copywriting Contract).
- **Display (96/900/0.95)** — canvas-drawn countdown numerals (`3`/`2`/`1`) and win/lose headline (`¡GANASTE!`). Close to today's `120px`/`72px`/`52px` mix, normalized to one consistent display size.

Only 2 weights declared (700, 900) — matches the existing HUD/canvas convention (nothing in the HUD/overlay layer currently uses a regular 400 weight; keep it that way).

Font family for the two DOM HUD roles above (Label, Body) switches from the legacy `'Courier New'` monospace "digital readout" look to `system-ui` bold sans, per D-13's instruction to begin moving HUD typography toward the new direction. The canvas-drawn Heading/Display roles (countdown, win/lose) already use `system-ui`/`sans-serif` today (`drawCountdown`/`drawWin` in `game.js`) — no change needed there, just keep it.

## Color

**This table governs the new chase-cam render world and the HUD chrome this
phase touches.** The lobby/create/join/rival/results screens keep their
existing Alpine blue/pink palette unchanged (out of scope this phase, per
CONTEXT.md's deferred "full HUD redesign" note) except for D-05's hide of the
multiplayer entry buttons.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#8FD4F0` → `#FFE3A6` (sky gradient) | Canvas sky/horizon backdrop behind the road — fills most of the visible frame in a chase-cam view. Bright, warm-tinted midday blue fading to a warm horizon glow. This is the palette anchor for "sunny day of karting in Argentina" (D-06), explicitly not gray/gothic. |
| Secondary (30%) | `#5C534A` (warm asphalt) + `#E4E0D6` (cream kerb) | Road surface, shoulders, kerb/rumble-strip bands, runoff ground. Warm gray-brown, not cool gray — keeps the road itself inside the same warm palette as the sky rather than reading as a desaturated placeholder. |
| Accent (10%) | `#F4A93A` (warm gold) | Reserved for: HUD active-state numerals (lap count, position badge text color), the alternating "on" stripe of the rumble strip, the finish-line stripe, and the speed-sensation edge-flash/shake vignette tint at high speed (RENDER-02). Do not use this gold for anything else — it is the one color players should learn means "speed / active state." |
| Destructive | `#EF4444` (existing, reused) | Reserved for: the existing wrong-way warning banner ("⚠ VUELTA INCORRECTA ⚠", unchanged behavior) and any error/blocked-state HUD text. No new destructive actions are introduced this phase. |

Accent reserved for: HUD lap/position numerals (active state), rumble-strip highlight stripe, finish-line stripe, speed-flash/shake vignette. Never use accent gold for generic buttons, borders, or decoration outside this list.

DOM chrome carried over unchanged (not re-specified here): `--blue #003087`, `--sky #00a0e9`, `--pink #f569b7`, `--dark #050a1a`, `--mid #0f1e3d` (see `style.css`) — these still govern the lobby/create/join/rival/results screens.

## Canvas Render Contract (Phase-5-specific — supplements the generic template)

The sections above cover DOM chrome. This section is the prescriptive contract
for the actual deliverable of this phase: the chase-cam pseudo-3D renderer
itself. All values are **starting points** for the executor, not final tuned
constants — exact numeric tuning is explicitly Claude's discretion per
CONTEXT.md, but each value below has a concrete default so the executor is not
guessing.

### Camera framing (D-10: tight and aggressive, OutRun/Mario Kart, not a pulled-back "readable" view)

| Property | Default | Rationale |
|----------|---------|-----------|
| Camera height above track | Low — roughly kart-eye-height, not a drone/behind-and-above view | "Low and close" per D-10; prioritizes speed sensation over sightlines |
| Camera distance behind kart | Close — kart occupies a visually prominent lower-third/-center of frame, not a small distant sprite | Matches classic OutRun/Mario Kart framing named in D-10 |
| Field of view / draw distance | ~100–120 segments (per RESEARCH/PITFALLS Pitfall 2 and RENDER-04) | Mobile frame-budget ceiling; also reinforces "tight" framing since a shorter draw distance naturally de-emphasizes far-ahead track reading |
| Canvas logical resolution | Keep the existing `480×640` logical/portrait backing store (`canvas.width/height` scaled by `devicePixelRatio`, unchanged from today's `initCanvasDPR()`) | Default — mobile-first portrait play is this game's proven baseline (touch controls dock bottom, HUD docks top); nothing in CONTEXT.md or research calls for a landscape/widescreen change, and a close/low chase-cam reads fine in a narrower portrait frame. Flag to the planner as a default, not a locked requirement — revisit only if playtesting the test loop shows the portrait frame feels cramped for a forward-road view. |

### HUD adaptation (D-11, D-12, D-13)

- **Keep, adapt in place:** lap counter (`hud-lap`), timer (`hud-timer`), position badge (`hud-pos`), role/gap indicator (`hud-role`). Same DOM elements, same top-docked bar structure — restyle per the Typography/Color sections above, do not rebuild from scratch.
- **Remove this phase:** the minimap (`drawMinimap()` and its call sites) per D-12 — the synthetic test loop isn't worth a minimap; returns in Phase 8.
- **Remove/hide this phase (derived from REQUIREMENTS.md's explicit "DRS is out of scope for v3.0"):** the DRS button (`#btn-drs`) and DRS HUD status/meter. DRS has no place in a kartodromo and is explicitly out of scope for the whole milestone (REQUIREMENTS.md Out of Scope table) — carrying it visually into the new chase-cam HUD would be inconsistent with that decision. This wasn't an explicit numbered CONTEXT.md decision (D-01..D-13 don't mention DRS directly) but follows directly from REQUIREMENTS.md; flagging it here so the executor doesn't accidentally re-project the DRS button onto the new view and then have to remove it again in a later phase.
- **Hide this phase (D-05):** multiplayer entry points — `#btn-create`, `#btn-join-screen`, and the `"MULTIJUGADOR EN LÍNEA"` divider — from the lobby screen, for the duration of Phases 5-9. VS CPU (both "GRAND PRIX · 22 AUTOS" and "DUELO · 1 VS 1") stays visible and fully playable.
- **Position badge range:** both VS CPU modes stay in scope this phase (D-05 only hides multiplayer, not solo/duel) — the position badge must still correctly render `P1/2` (duel) and `P1/22` (grand prix) ranges against the new chase-cam renderer's traffic-sprite compositing (see PITFALLS.md Pitfall 3 re: rival-car scale continuity).

### Art direction guardrails (D-06 through D-09)

- **Technique target:** hand-drawn/painterly, textured, atmospheric depth — reference is Hollow Knight: Silksong's *illustration technique*, explicitly **not** its dark/gothic mood.
- **Palette target:** bright, warm, sunny — see the Color section's dominant/secondary/accent values above. If any new art asset (kart sprite, sky, road texture) trends toward desaturated/gray/cool, that's a direction violation per D-06, not a style choice.
- **Track surface this phase:** reusing the existing `assets/r4a-tileset.png` (16-cell pixel-art tileset) as throwaway/functional texture source is explicitly correct per D-08 — do not invest in new track textures now, and do not treat the pixel-art road surface as a Color-section violation; it's intentionally temporary and exempted.
- **Kart/pilot sprite this phase:** per D-09, this should be an early *illustrated* (non-pixel-art) attempt, not a placeholder box — it should visually read as "moving toward Silksong-technique, bright/warm palette" even if rough, because it validates the view-angle-frame rendering approach the whole art pipeline depends on going into Phase 8.

### Test loop requirements (RENDER-03, D-02)

- Must be a **brand-new synthetic track**, not Monaco — `ROAD_SPINE` and the old top-down pipeline are retired and never referenced again starting this phase.
- Must include **at least one segment where a curve and a crest (elevation change) coincide** — this is the deliberate RENDER-03 test case that the renderer's curve+hill projection math must pass before any real track content is authored (PITFALLS.md Pitfall 1).
- Must read as a believable, drivable closed oval — exact shape is Claude's discretion (CONTEXT.md), but it needs to look intentional in the countdown overlay and during play, not like a bare debug ribbon.

### Mobile performance budget (RENDER-04)

- Draw-distance capped (~100-120 segments, see Camera framing above) and profiled on **real iOS Safari and a mid-tier Android device** before this phase is considered done — not desktop DevTools throttling as a substitute (PITFALLS.md Pitfall 2).
- All existing mobile/iOS fixes (lazy `AudioContext` init, Pointer Events touch controls, `devicePixelRatio`-aware sizing, viewport-fit layout) must be re-verified against the new renderer/HUD — this is a visual/interaction contract concern as much as a technical one, since a regression here directly breaks the touch-control HUD layout this document specifies.
